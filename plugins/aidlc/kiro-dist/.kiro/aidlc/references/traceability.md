# Traceability

Maintain an unbroken chain from business intent to release, so every requirement can be shown to be
designed, built, tested, and shipped — and gaps are visible.

## The chain
**Business Intent → Requirement (`FR-*`) → Unit/Epic → Story → Design / ADR → Test → PR → Build →
Release.**

Use stable identifiers and the existing backend mappings (don't invent a parallel id scheme):
- `FR-*` ids live in the PRD; Stories/Tasks carry them in their descriptions + labels (`FI-*`, `WSS`,
  `sprint-n`, work-item template).
- Design/ADR pages reference the FR ids they realise; tests cite the `AC-*` they prove; PRs reference
  the work-item key; the `scopeSignature`/release gate closes the chain.

## The report (generated by `/aidlc-progress`)
Produce a traceability report that walks the chain and flags:
- **Missing links** — an FR with no Story; a Story with no test; a merged PR with no work-item ref; an
  ADR nothing references.
- **Unverified requirements** — an `AC-*` with no executed test result (ties to
  `verification-checklist.md` — `NOT RUN` ≠ done).
- **Ungated changes** — a write/merge with no recorded approval (the guardrail approval record), or a
  HIGH-risk change with no specialist review/ADR (`risk-governance.md`).

Output a table: `FR id | Story | Design/ADR | Tests (pass?) | PR | Release | gaps`. Summarize counts
(covered / partial / missing) and list the specific gaps to close. It is a **report**, not an
auto-fix — a human decides what to do with the gaps.

## Note
Reuse what already exists: the PRD's `FR-*`, the work-item labels/links, the ADRs, and the guardrail
approval records are the data sources. Traceability is assembling and checking them, not adding new
bookkeeping.
