1What it is

AI-DLC (AI-Driven Development Lifecycle) treats the AI as a collaborator across the whole delivery cycle, not just an autocomplete. The plugin gives you a set of slash commands — /aidlc-* — that walk an idea through Intent → Elaborate → Design → Verify → Sprint → Review, producing shareable documents and real Jira tickets at each step.

Spec first

The bottleneck in AI delivery is specification quality, not typing. The plugin front-loads a testable PRD, a design, and acceptance criteria so the agent builds the right thing.

Human-gated

Every phase follows draft → approve → publish. The agent never writes to Confluence, Jira, or your repo without an explicit go.

Right-sized

Ceremony gears (quick / standard / deep) scale how much each step produces — the steps always run, only the volume changes.

One-line mental model: a PRD flows down into feature briefs, those into an Epic with sprints, those into designs + ADRs, those into richly-specified Jira tickets — and every artifact links back to the one above it, so nothing is built from a guess.

2The lifecycle

Six phases run in order, plus helpers you can call any time. Each phase reads the artifact the previous one produced and hands off to the next.

3Ceremony gears — right-sizing

The same steps run at three "gears." Light doesn't mean skipping steps or flattening the hierarchy — it means less content per artifact and fewer items. Set the default in aidlc.config.yaml (ceremony.default) or pick per feature.

PhaseQuickStandardDeep
IntentOne-page Feature Brief (with AC)Feature Brief (the light PRD)Full 21-section PRD
Elaboratefolded into the briefOne Epic + a few Stories/Tasks in one SprintMultiple Epics, full mob elaboration
Designfolded into "what we build"Short design note + only forced ADRs + Task SpecsFull domain model, ADR set, sequence diagrams
Verifyskipped (build from brief)Readiness + coherence → full ticket hierarchyFull rubric + confidence + cross-Epic fan-out

4The work hierarchy

The plugin speaks Jira: a Feature breaks into Epics, which hold Stories and Tasks, scheduled in Sprints. An Epic is a container that can hold several related features — so related work accumulates under one Epic rather than sprawling.

6The artifacts & templates

Each phase writes a document from a house template. All of them carry traceability — every item links back to the one above it.

PRD prd-template.md

The product-facing source of truth (21 sections): problem, goals, personas, functional requirements as machine-readable FR-* blocks, acceptance criteria (positive/negative/permission), business rules, roles, states, edge cases, and a Definition of Ready.

Feature Brief feature-brief.md

The light Intent output — one feature, ~2-minute read, still carrying mandatory AC, business rules, roles, states and edge cases.

Design Document design-doc-template.md

15 sections: a plain-language solution summary a PO/BA can validate, plus engineering detail (architecture, data model, APIs, error handling, algorithms, test strategy, traceability).

Work-item work-item-template.md

The GP-style Jira ticket body used for both Stories and Tasks: Overview, User Story, Scope, What to build, APIs, AC (Given/When/Then), Verification steps, Definition of Done, References.

ADRs

Architecture Decision Records for genuinely cross-cutting or shared-contract decisions — captured once, superseded not overwritten.

Constitution aidlc.constitution.md

A one-page statement of project principles & constraints that intent/design/verify check against. Links your standards rather than restating them.

7Execution rigor (the build half)

When code gets written, these mechanisms keep AI output trustworthy. They scale with the gear.

Recovery ledger

A machine-readable progress file that survives context compaction, so a resumed sprint never re-runs finished work.

Task briefs & context hygiene

Subagents get files, not pasted history — keeps the controller's context lean and cheap.

3-round fix-loop + adjudication

Findings are fixed over up to 3 scoped rounds; at the cap each is parked-with-ruling or BLOCK — no silent discards.

Review depth

A fresh reviewer on a different model, plus security/accessibility/performance specialist passes and reusable review memory.

Worktree isolation

Genuinely independent work runs in its own git worktree/branch/PR so parallel agents don't overwrite each other.

Evidence-led PRs

Merge confidence comes from a visible evidence pack (intent, test matrix, results, scans, rollback), climbed on an evidence ladder.

Test reliability

Role-based locators, auto-wait, deterministic mocks, negative/permission coverage, and mutation testing to prove the suite is real.

Token economics

Frontier models to plan/review, efficient models to implement; one task per session; pointers not payloads.

Agent toolchain

Guardrails for the coding agent: AGENTS.md rules, deny rules for secrets, PreToolUse hooks, least-privilege MCP, a repo-context layer.

8Who does what

AI-DLC keeps a human at every gate. Roughly:

The gate is always human. The agent drafts and proposes; a person approves before anything is published or merged.

9Worked example — QMetry360 iGen Workspace Setup

A real run at the Standard gear. One PRD produced three feature briefs; those became one Epic with three sprints; each sprint got a design + Task Specs; then the whole thing landed in Jira as 14 richly-specified work items.

Two decisions that became ADRs (and must not be quietly re-made)

  • Permission ceiling — the organisation's read grant is enforced server-side on every listing endpoint (a query predicate, not a UI filter), proven with a narrow-grant test fixture.
  • scopeSignature — a deterministic hash over the selected assets + history window; a shared contract with the downstream Validation & Activation feature, so changing it needs a new ADR.

This is the pattern to copy: the light lane still escalates genuine cross-cutting decisions to ADRs instead of burying them, while everything else stays a short note.

10Quick start

1Install & reload. Add the marketplace, install aidlc, then /plugin (Claude Code) or reload Cursor. Type / and confirm the /aidlc-* commands appear.

2Configure. Run /aidlc-init once — it writes aidlc.config.yaml and offers the Constitution + agent toolchain for your code repo.

3Capture the idea. /aidlc-intent — answer its questions; it drafts a PRD/brief and waits for your approval before publishing.

4Break it down. /aidlc-elaborate → /aidlc-design — Epic + sprints, then design + Task Specs. Approve each.

5Create tickets. /aidlc-verify — readiness + coherence check, then it creates the Jira hierarchy (after you say go).

6Build & review. /aidlc-sprint to implement TDD-first, /aidlc-review to merge with evidence. Close with /aidlc-retro.

Cheat sheet: init → intent → elaborate → design → verify → sprint → review. Anytime: help, progress, refactor, retro. Default gear standard; say "run this deep/quick" to change per feature.

11Good to know

  • The gates are instructions, not code. The plugin's quality depends on the agent following its skills — the draft→approve→publish gate, the evidence pack, the retro loop are behaviours, not hard-enforced locks. Keep a human at the merge.
  • Jira estimates use Original-Estimate hours where a project has no Story-Points field; enable the field if you plan in points.
  • Labels use hyphens (aidlc-sprint) — Jira rejects colons.
  • Works in both editors. Claude reads the skills/*/SKILL.md; Cursor reads mirrored .cursor/rules/*.mdc — same source of truth, kept in sync.
  • Config-driven. No org details are hardcoded; everything resolves from aidlc.config.yaml.
